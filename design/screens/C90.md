# C90 Targets and incentives

Surface: Web console (1440x900, responsive check 1024x768), Light and Dark. Route `/incentives` (SideNav "Targets and incentives"). Owners, directors and tenant admins write; auditors, accountants, cluster heads and store managers read; only owners and directors close a month.
Requirements: WC-009 (monthly targets, versioned incentive rules, payout preview, monthly close), VV-005 (verified visits only), SEC-028 (step-up), FA-024 (the officer app reads the same engine).

Implementation: `apps/console/components/growth/IncentivesView.tsx` and `RuleEditor.tsx` over `GET/PUT /v1/targets`, `GET/POST /v1/incentive-rules`, `POST /v1/incentive-rules/{id}/activate`, `GET/POST /v1/incentives/preview`, `GET /v1/incentives/payouts`, `POST /v1/incentives/close`. Rule-document validation: `validateDefinition()` in `lib/incentives.ts`.

## Layout

1. Header with the **month** select (the last 12 ended months; `?month=` in the URL; opens on the month before today).
2. **Verified visits note**, directly under the header and driven by the active rule document:
   - default: "Verified visits only: a visit counts towards eligibility and payout only when it passed the VV-003 checks. Unverified and partial visits are ignored." (info);
   - a document that widens `count_visit_statuses`: "This rule version counts visits with status verified, partial — not verified visits only. Confirm that is intended before publishing." (warning).
3. Tabs (`?tab=`): **Targets**, **Incentive rules**, **Payouts**.

### Targets

Subject select (Officers / Stores) and **Save targets** (enabled once something changed). Table: officer or store, verified visits, new farmers, sales (₹), collections (₹), own-brand share (bp) — every cell an inline number field for the write roles, plain text otherwise. Money is entered in rupees and sent as integer paise. Help line: "Targets drive the attainment multipliers in the incentive rules."

### Incentive rules

1. Version list: status chip (Active success, Retired neutral, Draft), "Version 3", name, "Active since 21 Jul 2026", and **Activate** for a draft (step-up).
2. **Rule editor** (read-only until "Edit as a new version"):
   - Eligibility: minimum verified visits, visit statuses counted (comma separated).
   - Components: id, metric, kind (Per unit / Slabs, per unit / Slabs, flat amount / Percent of a money metric / Flat amount above a threshold), the kind's own fields (rate per unit ₹, rate in basis points, threshold + amount, slabs with from / to / rate, the last slab open-ended), component cap.
   - Multipliers: metric (a plain metric or its attainment `%`), at-or-above, factor.
   - Total cap and "Claw back orders cancelled after their month".
3. Validation panel "Fix these before publishing" lists every problem (`incentives.ruleError.*`) — slab gaps, an open-ended last slab, percent on a non-money metric, duplicate ids, unknown metrics, invalid caps and multipliers.
4. **Publish version** (step-up): version name + "Publishing creates a new version and retires the previous active one. Payouts already closed are never recomputed."
5. **Payout preview**: officer select, "Preview payout" — posts the **unsaved** document, so the editor shows what the change would pay ("Previewing the unsaved rule document in the editor."). Result: eligible / not eligible chip with the reasons, a line per component (component, metric, value, amount, "capped"), then Gross, Clawback (danger when non-zero) and **Payable**. A closed month shows the frozen payout with a "Closed — frozen payout" chip.

### Payouts

Total payable tile, **Close month** (owners and directors, step-up, confirmation "Closing freezes every officer's payout for the month. It needs a one-time code and is recorded in the audit log."), and the frozen payouts table (officer, payout, status). Errors 409 `incentive_month_open` / `no_active_incentive_rules` surface in the dialog.
