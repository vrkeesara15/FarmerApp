# NF-005 API latency: p95 < 300 ms reads, < 600 ms writes

`make perf-api` runs `apps/api/tests/perf/test_latency.py` (never part of `make test-api` /
`make check-api`: `tests/conftest.py` ignores `tests/perf` unless `FARMERAPP_PERF=1`). It runs
on one pytest-xdist worker, so it gets a database of its own cloned from the migrated template
and dropped afterwards, and may commit.

## What it does

1. **Data**: the real seed job with the `FULL` profile, committed — tenant `fcc` with 5 stores,
   200 farmers (285 farms, 403 crop plots), 5 field officers, 7 duty days with ~216 visits and
   their photos / confirmations / tracks, the M3 catalogue, stock, orders, payments and khata;
   plus tenant `gfl`. Then the nightly rule batch (`run-rules --mode batch`) so the flag inbox
   is realistic, then `ANALYZE` as the owner (production tables have planner statistics from
   autovacuum; see "Findings" for why this matters).
2. **Load**: the real app (`create_app()`, every request its own session and transaction)
   driven through `httpx.ASGITransport` — in-process, no TLS, load balancer or network hop —
   with `PERF_CONCURRENCY` requests in flight (default **4**: the pilot's 5 officers syncing
   plus console users) in **one Python process**, like one Cloud Run instance.
3. **Measure**: per endpoint 8 unmeasured warm-up calls, then `PERF_SAMPLES` (default 80)
   measured calls; p50 / p95 of the wall time of each call. The Markdown table goes to
   `apps/api/perf-report.md` (git-ignored) and the test fails when a p95 is over its budget.

| Endpoint | Caller | Kind |
|---|---|---|
| `GET /v1/me` | officer | read |
| `GET /v1/farmers?limit=50` | officer, owner | read |
| `GET /v1/visits?limit=50` | cluster head, owner | read |
| `GET /v1/analytics/owner-home` | owner | read |
| `GET /v1/flags?limit=50` | owner | read |
| `GET /v1/catalog/products?store_id=` | store manager | read |
| `POST /v1/sync` — 20 ops (16 registrations + 4 edits), incremental cursor | officers, round robin | write |
| `POST /v1/sync` — 50 ops (backlog after a day offline) | officers | write (per-op budget) |
| `POST /v1/visits/check-in` | officer, a farm of their own farmers | write |
| `POST /v1/orders` | officer | write |
| `POST /v1/payments` (card, one open order each) | store manager | write |

Sync batches are the heaviest ops (registrations run the VA-F01 / F02 / F03 / F06 rules) with
distinct synthetic names in the officer's own villages; batches in flight at the same time come
from different officers, as in the field. Each device made its first full pull before the
measurement and syncs incrementally with its cursor (the app's steady state; upload every 15
minutes, `sampling.upload_s`).

**Sync budget.** A 20-op batch (a 15-minute outbox) is held to the 600 ms write budget. The
50-op backlog batch is held to the same budget per op spread over a typical batch:
50 / 20 x 600 ms = **1,500 ms**. A single request carrying 50 writes cannot be compared with a
single write; see "Recommendations" for the SLO consequence.

## Results

Machine: Apple M5 (10 cores, 32 GB), macOS 26 (Darwin 25.4.0 arm64), Python 3.12.13;
PostgreSQL 16.15 + PostGIS 3.6 in Docker Desktop (10 CPUs, 7.75 GB), 2026-09-19.

**Concurrency 4 (the default; the gate)** — all within budget:

| Endpoint | n | p50 ms | p95 ms | budget ms |
|---|---|---|---|---|
| GET /v1/me | 80 | 8 | 60 | 300 |
| GET /v1/farmers (officer) | 80 | 14 | 16 | 300 |
| GET /v1/farmers (owner) | 80 | 15 | 16 | 300 |
| GET /v1/visits (cluster head) | 80 | 20 | 21 | 300 |
| GET /v1/visits (owner) | 80 | 19 | 24 | 300 |
| GET /v1/analytics/owner-home | 80 | 118 | 203 | 300 |

| GET /v1/catalog/products | 80 | 31 | 35 | 300 |

**Concurrency 1** (`PERF_CONCURRENCY=1 PERF_SAMPLES=40`): owner home p95 61 ms, sync 20 ops
p50 202 / p95 221 ms, sync 50 ops p50 604 / p95 724 ms, every other endpoint p95 < 50 ms.

**Concurrency 8** (`PERF_CONCURRENCY=8`) — over budget: owner home p95 326 ms, sync 20 ops p95
912 ms, sync 50 ops p95 2,051 ms (every other endpoint p95 < 220 ms). Latency grows linearly
with concurrency because the work is CPU-bound in one Python process (SQLAlchemy ORM + ~15
statements per sync op); eight concurrent heavy requests share one core. In production this
is the Cloud Run `concurrency` / `max_instances` trade-off, not a query problem (see
"Recommendations").

## Findings and fixes (this change)

| Before (concurrency 8, first run) | Cause | Fix |
|---|---|---|
| `POST /v1/sync` (40 registrations + 10 edits) p50 8.0 s, p95 11.5 s (first version of the suite: full pulls without a cursor, near-identical names in one village — both also fixed in the suite) | every registration ran the inline (VA-F01 / F02 / F03) and `farmer.registered` (VA-F06) rules on its own, each reading the tenant row and slug again | `rules.engine.deferred(session)`: inside a sync batch, `run_inline` / `emit` calls are collected and each rule runs **once per batch** with the union of subject ids (same transaction, same flags); tenant slug cached per session; `get_tenant_settings` cached per session (bypassed when the tenant row is modified in the session) |
| VA-F06 shared-device query 3.3 ms per registration, growing with the audit trail | `audit_log` scanned for every `farmer.create` of the tenant | partial index `ix_audit_log_farmer_create_device (tenant_id, device_id) WHERE action = 'farmer.create'` (Alembic 0026); the subject lookup now filters `entity = 'farmer'` so it uses `ix_audit_log_tenant_entity_created` |
| VA-F02 "same phone" self-join ~0.8 ms x 2 per registration | one join with `OR` (hash or digits of the legacy plain phone) defeated the `(tenant_id, phone_hash)` index | two joins: by hash (index), and the legacy digits join only over rows that still carry a plain phone |
| `GET /v1/analytics/owner-home` p95 446 ms | the open-flags trend ran one count query per bucket (30+ queries) | `FlagCountsPort.open_totals(query, instants)`: one query with a `FILTER` aggregate per bucket |
| Full sync pull 1.4–2.9 s on a freshly loaded database | the change-feed scope (an `OR` of 14 `IN (subquery)`) without planner statistics: row estimates of 1, nested loops, `loops=85486` | not a code change: production tables are analysed by autovacuum; the suite analyses after seeding (46 ms with statistics). **Run `ANALYZE` after bulk imports** (onboarding a tenant, restores) — noted in the Cloud SQL runbook follow-ups |

Also checked and fine: every hot read is a handful of indexed queries (`GET /v1/farmers`,
`/v1/visits`, `/v1/flags` 4–8 statements, no N+1); check-in, order and payment writes stay
under 100 ms p95 at concurrency 4 with the SEC-026 encryption and SEC-024 integrity code paths
in place. JIT (`jit = on` in the image) was ruled out as the cause of the slow feed.

## Recommendations (follow-ups)

1. **Sync SLI**: the write-latency SLO (`infra/modules/monitoring/slo.tf`, all POST / PUT /
   PATCH / DELETE) includes `/v1/sync`, whose latency scales with the batch. Give sync its own
   latency objective (per op, or per batch of <= 25 ops) and exclude `/v1/sync` from the write
   SLI, or cap the app's outbox batches at 25 ops (`maxOpsPerSync` is 200 today).
2. **Cloud Run concurrency**: keep the API's container concurrency low enough per vCPU that
   heavy requests do not queue behind each other (4–8 per vCPU), and let instances scale out.
3. **Per-op round trips in sync** (~15 statements per registration: savepoint, idempotency
   lookup, duplicate checks, inserts, audit and change-feed rows, the detail reload): prefetch
   the batch's `sync_op` rows in one query and batch the audit / change-feed inserts per flush.

## Human gate

These are in-process numbers on a laptop: they catch N+1 queries, missing indexes and slow
code. Production numbers need a **load test against Cloud Run + Cloud SQL in stg** (TLS, load
balancer, Cloud Armor, the Cloud SQL connector and real instance sizes), e.g. k6 or Locust with
the same endpoint mix and realistic think times — a human runs it before the pilot and records
the results here. The SLO alerts (read / write p95 for 15 min) then watch production.
