# NF-007 scale: 50 tenants, 5,000 officers, 2 million farmers, 20 million photos

SPEC 7: *"50 tenants, 5,000 officers, 2 million farmers, 20 million photos without
re-architecture."*

`make scale-api` runs `apps/api/tests/scale/` (never part of `make test-api` / `make check-api`:
`tests/conftest.py` ignores `tests/scale` unless `FARMERAPP_SCALE=1`). It runs on one
pytest-xdist worker, so it gets a database of its own cloned from the migrated template and
dropped afterwards, and may commit. Report: `apps/api/scale-report.md` (git-ignored).

## The arithmetic that decides what to measure

The target divides into **40,000 farmers per tenant** (2,000,000 / 50) and **100 officers per
tenant** (5,000 / 50), with 10 photos per farmer (20,000,000 / 2,000,000). That matters more
than it looks: every request in this system is scoped to one tenant by RLS, so *the target is
reached by adding tenants, not by growing one*. A tenant-sized workload is therefore the thing
to measure, and the per-request numbers below **are** the numbers at target — not a fiftieth
of them.

What genuinely grows with 50 tenants is the total on disk, autovacuum work, connection demand
and anything that iterates tenants. Those are addressed in "Multi-tenant hygiene at scale" below.

So the suite seeds **one tenant at 1/50th of the totals**:

| Table | Rows seeded | Total at 50 tenants |
|---|---:|---:|
| `farmer` | 40,015 | 2,000,750 |
| `visit` | 40,010 | 2,000,500 |
| `visit_photo` | 400,010 | 20,000,500 |
| `diagnosis` | 19,971 | 998,550 |
| `order` | 20,032 | 1,001,600 |
| `location_point` | 105,118 (7 days × 100 officers × 150) | 5,255,900 |
| `user` (field officers) | 100 | 5,000 |

Generated with `INSERT ... SELECT ... FROM generate_series` (`tests/scale/synthetic.py`), not
the ORM: 40,000 mapped objects would measure SQLAlchemy rather than Postgres and would take
minutes. Every insert runs as the ordinary **app role inside the tenant's binding**, so RLS
applies exactly as in production — the `WITH CHECK` on every policy is exercised ~840,000
times per run, which is itself part of the evidence. Seeding takes **~12 s**.

## Results

Machine: Apple M-series (10 cores), macOS 26 (Darwin 25.4.0 arm64), Python 3.12.13;
PostgreSQL 16 + PostGIS 3.6 in Docker Desktop. 2026-09-21. 40 samples per endpoint after 5
warm-up calls, in one Python process through `httpx.ASGITransport` (no TLS, no load balancer,
no Cloud SQL network hop). Whole run: **~63 s**.

## Query plans that mattered

Each plan is `EXPLAIN (ANALYZE, BUFFERS)` against the seeded tenant after `ANALYZE` (a freshly
loaded database has no planner statistics, and without them every plan below is judged on a
fiction — the same reason `make perf-api` analyses). The suite **fails** when a request-path
plan reads more than 5,000 rows of a watched table sequentially; the two exceptions are named
in the code (`KNOWN_WIDE`), never silently passed.

### The indexes this exercise added (Alembic `0042`)

Before them these plans sorted or scanned the whole tenant to return 50 rows.

| Index | Table | Why |
|---|---|---|
| `ix_farmer_tenant_created_id` | `farmer` | `GET /v1/farmers` is a keyset page ordered by `(created_at, id)` within the tenant. Now: `Index Scan Backward … rows=50 … Execution Time: 0.127 ms` over 40,015 rows. |
| `ix_visit_tenant_created` | `visit` | The visits list and the field-team windows read by age for the *tenant*, not by officer, so `ix_visit_tenant_officer_checkin` could not lead. |
| `ix_diagnosis_tenant_created` | `diagnosis` | Same shape for the diagnosis list and the AN-007 counts. |
| `ix_corpus_image_tenant_status_created` | `corpus_image` | The WC-007 corpus manager pages approved images by age. |
| `ix_order_tenant_created` | `order` | The store day views and AN-003 read orders by age per tenant. |
| `ix_visit_photo_tenant_created`, `ix_farm_photo_tenant_created` | photos | Bound the WC-014 recount and the NF-012 photo sweep to a month. |

`location_point` needed nothing: it is already partitioned daily (Alembic `0010`). One
officer's day reads **one partition** and prunes the other seven —
`Subplans Removed: 7`, `Index Scan using location_point_p…_tenant_id_officer_id_ts_idx`,
`Execution Time: 0.557 ms` over 105,118 rows. Partitioning is the right answer at this volume
and stays right at 5.3 million.

### The finding that is *not* an index problem

**`GET /v1/analytics/owner-home` is O(rows in the range), in Python.**

```
Seq Scan on visit  (cost=0.25..2144.55 rows=40003 width=76)
                   (actual time=0.004..10.226 rows=40010 loops=1)
  Filter: (deleted_at IS NULL AND tenant_id = … AND checkin_at < now()
           AND checkin_at >= (now() - '30 days'::interval))
  Rows Removed by Filter: 2
Execution Time: 15.052 ms
```

The sequential scan is **correct**: the query returns 40,010 of 40,012 rows, and no index can
beat a sequential scan that has to return 99.99% of what it filters. Postgres does its part in
**15 ms**. The other ~900 ms is Python: `analytics/facts.visits()` materialises one `VisitFact`
per visit and `analytics/facts.activity()` does the same for orders, and `kpi.active_counts`
then walks the per-farmer date sets once per trend bucket. Profiled
(`cProfile`, same data): `facts.activity` ≈ 66 ms per call × ~7 calls, `facts.visits` ≈ 61 ms
per call × ~4.5 calls, per request.

**Judgement.** This is inside its WC-001 budget ("loads in under 3 s") one request at a time,
and outside it at four concurrent requests on one instance. It is not a re-architecture: it is
one bounded refactor — push the visit and activity aggregation into SQL (`GROUP BY` over the
range, the way `facts.sales_aggregate` already does for money) and return counts instead of
rows. Until then the mitigation is horizontal: Cloud Run `concurrency` for the console traffic,
which is the trade-off `docs/deploy/configuration.md` already documents. Logged as the M8
follow-up in `docs/progress.md`; the scale suite names it in `KNOWN_WIDE` so it cannot be
forgotten, and the WC-001 3-second assertion will catch any regression beyond it.

The second named wide scan is `SELECT count(*) FROM visit_photo … last 30 days`
(133,337 rows per parallel worker, 61 ms). That query is the `usage-recount` **job** and the
NF-012 sweep, never a request — and the reason the WC-014 counters are incremental in the
first place.

## Multi-tenant hygiene at scale

* **RLS holds on the new tables.** `platform_tenant`, `usage_counter` and `billing_statement`
  go through `enable_rls` in Alembic `0042` and are covered by the `tests/rls/test_meta.py`
  catalogue check like every other table. `tests/platform/test_authz.py` proves the registry is
  invisible from inside a tenant (a session bound to a customer tenant counts **zero**
  `platform_tenant` rows while the platform admin lists them) and that a `platform_admin` role
  string on a user in a customer tenant still gets 403 — the guard is role **and** tenant.
* **Every plan above carries `One-Time Filter: (app_current_tenant() = …)`.** That is the RLS
  policy in the plan: isolation is not bypassed anywhere in this suite, including the 840,000
  synthetic inserts, which all pass the policies' `WITH CHECK`.
* **Per-tenant jobs stream.** `platform_admin.jobs.all_tenant_ids` pages the registry 200 rows
  at a time and yields; `run_recount` and `run_statements` open **one transaction per tenant**
  and hold one tenant's working set at a time. No job loads "all tenants".
* **Connection budget.** Adding tenants adds no pools — a pool belongs to a *process*
  (`infra/modules/db_budget`). What more tenants add is concurrent requests, which raises
  `max_instances`, and the budget is a function of that. The SaaS shape is now a case in
  `infra/modules/db_budget/tests/budget.tftest.hcl` and a note in
  `docs/deploy/configuration.md` ("Connection budget"): at 50 tenants the api ceiling has to
  rise, `sql_max_connections = 250` stops fitting, and the plan fails loudly rather than
  exhausting Cloud SQL silently.

## What must be re-measured in the cloud — HUMAN GATE

Everything above is one Python process against a Docker Postgres on a laptop: no TLS, no load
balancer, no Cloud SQL network hop, no cross-AZ latency, no other tenants' traffic. The
*shapes* carry over (a plan that is O(tenant size) here is O(tenant size) in Cloud SQL); the
*numbers* do not. Before the SaaS milestone a human must:

1. **Load-test on stg** with the prd-shaped Cloud SQL tier (`db-custom-2-7680`), a real Cloud
   Run deployment and traffic from outside the VPC. Re-measure every row of the concurrency-1
   and concurrency-4 tables, and find the Cloud Run `concurrency` / `max_instances` pair that
   keeps owner home inside WC-001.
2. **Size the instance for 50 tenants**: 20M photo rows, ~2M farmers and ~5.3M location points
   is roughly 50 × this run's footprint. Check disk, shared buffers, and whether
   `location_point` retention (180 days, NF-012) keeps the partition count sane.
3. **Re-run the connection budget** against the chosen `max_instances` and raise
   `sql_max_connections` if the plan refuses — a change that restarts the instance and belongs
   in a maintenance window (already a documented human gate).
4. **Watch autovacuum** on `visit_photo` and `location_point` at 50 tenants; the OPS-003
   dashboards have the metrics.
5. **Decide the owner-home refactor** before onboarding a tenant with a full-size month of
   visits, or accept the Cloud Run concurrency cost.

## WC-014 acceptance evidence: a new tenant in under 30 minutes

`tests/platform/test_onboarding.py` walks the whole onboarding as API calls and writes
`apps/api/onboarding-report.md`. Measured run: **491 ms for 8 API steps** —

| # | Step | Cumulative ms |
|---|---|---:|
| 1 | create + provision the tenant | 113 |
| 2 | invite the primary contact | 137 |
| 3 | the new admin logs in (OTP) | 163 |
| 4 | set branding | 172 |
| 5 | first store | 178 |
| 6 | add a field officer | 191 |
| 7 | register a farmer | 400 |
| 8 | record a visit (check-in + check-out) | 491 |

What that proves is the part a test can prove: **there is no manual step and no code change
between "create the tenant" and "a farmer visit is recorded"**. The 30 minutes in SPEC 2.5 is
a human budget around this half-second — a human gate, to be timed once with a real operator,
a real phone and a real SMS.
